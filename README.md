# Мини-CRM «Объекты и задачи»

CRM для строительной компании: постановщики создают объекты и назначают задачи, исполнители выполняют их и отправляют на проверку.

## Стек

- React + TypeScript.
- Vite.
- Supabase: PostgreSQL, Authentication, API и правила доступа.
- Оформление на CSS без UI-библиотеки.

Отдельного сервера приложения нет. Фронтенд обращается к Supabase, а права доступа и переходы статусов проверяются в базе.

## Возможности

**Постановщик:**
- Просмотр всех объектов и задач.
- Создание, редактирование и удаление объектов и задач.
- Назначение и смена исполнителя.
- Принятие задач или возврат на доработку с обязательным комментарием.

**Исполнитель:**
- Просмотр своих задач и объектов, где они находятся.
- Раздел «Мои задачи».
- Взятие задачи в работу и отправка на проверку.

Обеим ролям доступна история видимых им задач.

## Локальный запуск

Нужны Node.js 22.12+ и npm.

```bash
git clone https://github.com/lev0000000/test-crm.git
cd test-crm
npm ci
```

Создайте в корне проекта файл `.env.local`:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
```

Значения берутся из настроек проекта Supabase. Используйте публичный publishable/anon key. Секретные ключи `service_role` и secret key здесь не допускаются.

Запустите приложение:

```bash
npm run dev
```

Откройте адрес из терминала. После изменения переменных окружения перезапустите сервер разработки.

Команды проекта:

```bash
npm run dev      # Разработка
npm run build    # Проверка TypeScript и сборка в dist
npm run preview  # Локальный просмотр сборки
npm run lint     # Проверка кода Oxlint
```

## Развёртывание базы Supabase

### 1. Создание проекта

Создайте проект Supabase и сохраните его URL и публичный ключ.

### 2. Применение миграции

В новом проекте откройте SQL Editor, вставьте содержимое:

```text
supabase/migrations/001_crm.sql
```

Выполните запрос. Миграция создаёт типы, таблицы, индексы, правила доступа, функции и триггеры.

Миграция предназначена для первоначального развёртывания. Повторно запускать её в уже настроенной базе не нужно. Последующие изменения следует оформлять отдельными SQL-миграциями.

Изменение SQL-файла в репозитории само по себе не меняет облачную базу — запрос необходимо выполнить в Supabase.

### 3. Отключение регистрации

В настройках Authentication отключите `Allow new users to sign up`.

Пользователей создаёт администратор вручную.

### 4. Создание пользователей

В Authentication → Users создайте минимум:
- одного постановщика;
- двух исполнителей.

Для тестовых аккаунтов включите автоматическое подтверждение email.

Затем создайте профили через SQL Editor, подставив реальные UID аккаунтов:

```sql
insert into public.profiles (id, display_name, role)
values
  ('MANAGER_UID', 'Постановщик', 'manager'),
  ('EXECUTOR_1_UID', 'Исполнитель 1', 'executor'),
  ('EXECUTOR_2_UID', 'Исполнитель 2', 'executor');
```

UID берутся из Authentication → Users. Они отличаются в каждом новом проекте.

Аккаунт в Authentication отвечает за вход, запись в `profiles` — за имя и роль. Без профиля доступ к рабочему пространству не предоставляется.

### 5. Демоданные

Войдите постановщиком и создайте 2–3 объекта с задачами для обоих исполнителей.

Под исполнителями возьмите часть задач в работу и отправьте на проверку. Под постановщиком примите одну задачу и верните другую с комментарием. Так формируются разные статусы и настоящая история изменений.

## Устройство базы

- `profiles` — имена и роли сотрудников, связанные с `auth.users`.
- `projects` — названия и адреса объектов.
- `tasks` — задачи, исполнители, авторы и текущие статусы.
- `task_history` — события создания и смены статуса.

Один объект содержит несколько задач, одна задача — несколько записей истории.

## Статусы

Разрешены только следующие переходы:

```text
Новая → В работе                  Исполнитель
В работе → На проверке            Исполнитель
На проверке → Принята             Постановщик
На проверке → На доработке         Постановщик, с комментарием
На доработке → В работе            Исполнитель
```

Исполнитель выполняет действия только над назначенной ему задачей.

## Безопасность

- Supabase Auth проверяет email и пароль и выдаёт сессию пользователя.
- RLS ограничивает доступ к конкретным строкам таблиц.
- Исполнитель видит только свои задачи и связанные с ними объекты.
- Редактирование объектов и удаление задач доступны только постановщикам.
- Триггер `guard_task` проверяет переходы статусов и запрещает исполнителю менять данные задачи.
- Триггер `record_history` автоматически записывает историю в той же транзакции, что и изменение задачи.
- Пользователям не выданы права на прямое добавление, изменение и удаление записей истории.
- Роли назначаются администратором через базу, а не через интерфейс.
- Функция `transition_task` проверяет ожидаемый статус и блокирует строку на время изменения, защищая от конфликтующих переходов.
- Во фронтенде используется только публичный ключ Supabase.

Ограничения интерфейса служат для удобства. Проверки базы продолжают действовать при прямых запросах к API.

SQL Editor работает с административными правами. Само по себе отображение всех строк в SQL Editor не означает, что они доступны обычному пользователю.

## Публикация на Vercel

1. Отправьте исходники в GitHub.
2. Импортируйте репозиторий в Vercel.
3. Укажите:
   - Framework: Vite.
   - Build Command: `npm run build`.
   - Output Directory: `dist`.
4. Добавьте переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
5. Запустите Deploy.

Переменные Vite подставляются во время сборки. После их изменения необходим новый deployment.

База разворачивается отдельно в Supabase. Публикация фронтенда на Vercel не применяет SQL-миграции.

## Тестовые аккаунты

В текущем демонстрационном проекте:

- `admin@mail.ru` — ADMIN, постановщик.
- `user@mail.ru` — USER, исполнитель.

Пароли передаются отдельно в сообщении о сдаче и не хранятся в репозитории. Для полного демонстрационного сценария требуется также второй исполнитель.

При развёртывании в новом проекте аккаунты и профили необходимо создать заново.

## Решения и ограничения

- Постановщики имеют общий доступ ко всем объектам и задачам.
- У сотрудника одна роль.
- Исполнителем задачи может быть только пользователь с ролью `executor`.
- Объект выбирается при создании задачи; перенос между объектами в интерфейсе не реализован.
- Удаление объекта удаляет его задачи и историю. Удаление задачи удаляет её историю.
- История содержит создание задачи и смены статусов; изменения описания и назначения отдельно не журналируются.
- Имена и роли сотрудников доступны вошедшим пользователям как справочник.
- Навигация реализована состоянием React, без отдельных URL карточек.
- После обновления страницы выбранная карточка сбрасывается.
- Данные обновляются после действий и повторного открытия экранов; подписки на изменения в реальном времени нет.
- Название объекта отдельно в карточке задачи пока не отображается.
- Автоматические тесты не добавлены. Успешная сборка не заменяет проверку прав через API.

## Объяснение для руководителя

Система объединяет стройки и задачи команды. Руководитель создаёт объект, назначает работу сотруднику и получает её на проверку. Сотрудник видит только свои задания, берёт их в работу и отправляет результат на проверку. Руководитель принимает задачу или возвращает её с пояснением, что исправить.

Каждая смена статуса сохраняется автоматически: кто выполнил действие и когда. Историю нельзя исправить через приложение. При удалении самой задачи её история также удаляется.
